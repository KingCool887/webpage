# Local website viewer prototype

The launcher is a single browser-like window and runs entirely on the laptop. The address bar sits at the top: type a website address, press Enter, and the site loads in the area below. No load button is needed. The small selector next to the address bar chooses how the page is loaded:

- **Streamed** (default) launches a hidden, temporary Chrome profile, loads the target directly in that browser, and sends JPEG frames plus mouse/keyboard input to the launcher window. This keeps the target page at its real origin and avoids rewriting its assets, which makes it the mode to use for browser games. The hidden page is brought to the front with focus emulation, so its own `requestPointerLock()` gets a real pointer lock from Chrome and the game receives trusted relative movement; the launcher additionally captures the real cursor and feeds it unbounded movement, so turning does not stop at a screen edge. If the hidden browser refuses the native lock, the launcher falls back to a page-level virtual lock with trusted movement clamped to the viewport (turning then stops at the edges). Escape releases the launcher's capture (and the game's lock), and toolbar clicks are never forwarded while the game holds the mouse. The game's own full-screen request enters or leaves launcher full screen, which hides the address bar. The browser's F11 key still works, and Escape leaves full screen. The prototype does not stream audio and performance depends on the laptop.
- **In-page** sends the page through a local reverse proxy and displays it inside the launcher window. Input, audio, full screen, and pointer lock then run natively in the browser, so there is no capture/encode/relay latency; the iframe is granted `fullscreen` and `pointer-lock` permissions. It rewrites common links and dynamically assigned frame/resource URLs, strips frame-blocking headers, and buffers finite Fetch request bodies (up to 32 MB) to support local HTTP/1.1. Proxy hostnames are opaque per source host. WebSocket constructors are left native (games often reject a monkey-patched one); sockets that use a party server at "proxy port + 1", or a relative `/ws` path on the proxy port, are relayed to `party.<target host>` with the page's own origin. That is what lets the Deadshot client boot, join, and show its online count. The launcher's Diagnostics panel also shows in-page errors reported by the proxied page: script errors, failed resources, console errors, and the game's own error reports, with URLs reduced to their path after the proxy token.

The PowerShell window prints per-request proxy diagnostics by default. The **Diagnostics** button in the launcher shows both modes: in-page errors reported by the proxied page, and the streamed-browser log saved to `stream-diagnostics.log` in this folder. Streamed diagnostics report viewport sizes, full-screen requests, pointer-lock state, and the WebGL renderer given to the hidden page, without recording the target URL. In-page messages are capped; resource and stack URLs are reduced to the path after the proxy token, while a game's own error report is shown as the game sends it. Proxy log lines show the opaque local proxy host, method, status, elapsed time, and response type; the real target host and path are not printed, so the helper window does not reveal the site. The target is still visible to someone who inspects DevTools, the browser cache, or the decoded token in a proxied URL. Requests blocked by a browser extension before reaching the local proxy will not appear in these logs; they appear only in browser DevTools.

## Performance notes

- The hidden browser starts with GPU acceleration enabled (`--enable-gpu --use-angle=d3d11`) and with background throttling disabled. Without that, headless Chrome fell back to the Microsoft Basic Render Driver (software WebGL), which made browser games run slowly and made their input feel delayed. The Diagnostics log records the renderer as a `page webgl ...` line, so you can confirm the real GPU is in use.
- Input is sent in small batches, and mouse movement is coalesced to the newest position. While the game holds the mouse, the launcher takes a real pointer lock and feeds unbounded movement into the hidden page. The hidden page normally takes a real pointer lock of its own (see above), so it receives trusted mouse events; only when that is refused does the launcher fall back to trusted movement clamped to the viewport, which stops at the edges. The Diagnostics log shows which one is active as `lock=true/native` or `lock=true/virtual`. The helper hands commands to the hidden browser without waiting for each reply, so a busy game cannot make the launcher fall further and further behind.
- The viewer is kept current rather than replayed in order: if it cannot consume frames quickly enough, older frames are skipped so the picture stays close to real time. Frames are JPEG quality 60. A page that never repaints shows as `idle` in the status pill instead of a frame rate.

The helper binds to loopback (`127.0.0.1`) and the proxy uses `.localhost` names that resolve back to the laptop. The launcher uses port 8787, the site proxy 8788, and a party-socket relay 8789 (all loopback). It does not configure the router or accept connections from other devices.

## Start it

1. Make sure Google Chrome and Node.js are installed.
2. Double-click `Start-Game-Window.ps1`. If Windows blocks scripts, open PowerShell in this folder and run `./Start-Game-Window.ps1`.
3. Keep the PowerShell window open while using the launcher.
4. Open `http://launcher.localhost:8787` in your regular browser, type a website address, and press Enter. You can omit `https://`; it is added automatically. **Streamed** is selected by default; choose **In-page** in the small selector for the HTTP proxy instead.
5. Watch the PowerShell window for request statuses when using **In-page**. `4xx`, `5xx`, or `502` entries point to requests the proxy could not complete. A browser-side `ERR_BLOCKED_BY_CLIENT` may have no matching server log because the request never reached the proxy.

Your existing launcher can link to or embed `http://launcher.localhost:8787` while the helper is running.

## Limits and visibility

- In in-page mode, the address bar stays on the launcher page. DevTools shows requests to an opaque `.localhost` proxy host. The target is encoded in the proxy path, so it is not human-readable at a glance, but Base64 is reversible.
- The proxy must know the real target URL to fetch it. The laptop's browser and local helper are not a secure boundary against someone who can inspect the machine.
- The website sees requests from the laptop's network connection in both modes. This prototype is for keeping the target URL out of the visible top-level address bar, not for hiding the user from the site.
- This reverse proxy is experimental. Opaque proxy names can avoid simple URL filter rules, but browser extensions can still block requests based on other signals. Cookies are scoped to the opaque host that set them, so authentication spanning multiple subdomains may fail. It rewrites common HTML and CSS URLs, removes CSP/frame headers, relays WebSockets, and buffers finite Fetch request bodies, but sites with complex JavaScript, service workers, login, DRM, anti-bot checks, long-lived streamed uploads, or unusual APIs can still fail. Web Workers and ES modules are not yet rewritten inside the worker, so engine loaders that fetch from workers can fail; the in-page diagnostics panel is the place to see that. A game that checks its own origin or runs anti-tamper/adblock checks may refuse to start through any proxy. Browser games may be too demanding or incompatible.
- The proxy keeps upstream caching for non-HTML assets and always serves rewritten HTML uncached. A stalled or aborted download is dropped without taking the helper down.
- The embedded page is not sandboxed, so sites can open popups or navigate the top-level page. The launcher and proxy are on different origins, which prevents the embedded site from reading the launcher's page data. In in-page mode the site's own full-screen requests go to the embedded frame, not to the launcher chrome.
- Streamed mode uses a temporary Chrome profile under the operating system temp folder and removes it when the stream stops or the helper exits. The target URL is not printed in the helper log or passed as a command-line argument, but it can be seen by someone inspecting the running browser via local debugging tools. Closing the stream deletes that temporary profile. Audio is not included yet; high-frame-rate games may feel laggy. In the hidden page, pointer lock is native when Chrome accepts it (the helper brings that page to the front and emulates focus) and otherwise falls back to a page-level virtual lock; full screen stays a page-level emulation. The hidden browser has no visible window, so there is no real OS full screen there, but the launcher's own pointer lock is a real browser lock so the cursor is captured and relative movement never hits a screen edge. If the launcher is embedded in a frame that does not allow pointer lock, it falls back to absolute cursor movement, which is limited by the screen edges. Because browsers only allow full screen and pointer lock from a user gesture, the launcher enters them when the page asks and the gesture is still recent, otherwise on the next click inside the stream. Press Escape to release the mouse capture before using the launcher toolbar. If the hidden browser fails to start or shows a blank stream because a machine has no usable D3D11 GPU, remove `--enable-gpu` and `--use-angle=d3d11` from `server.js` to return to software rendering.
- The top-level address is the launcher's local address, not `about:blank`. Replacing it with a working `about:blank` page would require direct browser automation, and would not conceal the page from DevTools.

This is a local prototype and has not been tested against a particular site or launcher embedding setup.
